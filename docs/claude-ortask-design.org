* Overview

This document describes the design for the local task CLI and the org-mode task
format it reads.  It incorporates feedback from the Codex and Gemini design docs
in this directory.

Goals:

1. Use standard org-mode conventions so that Emacs users can edit and
   organize tasks naturally (folding, refile, archive, agenda, etc.)
2. Assign stable task IDs (=t0001= through =t9999=) for reference in
   notes, chatlogs, and tooling
3. Keep =status.py= useful as a CLI for querying and updating tasks,
   including use by LLMs and shell scripts

* README.org TODO section format

** Heading structure

Tasks preferably live under a top-level =* Tasks= heading, but ortask can also
use valid task headings across a file when that section is absent. Each task is
a standard org-mode heading with a TODO/DONE keyword and a stable ID:

#+begin_example
,* Tasks
,** DONE t0001 Initialize LLMs in this directory
,*** DONE t0001.1 ChatGPT/codex
,*** DONE t0001.2 Gemini
,*** DONE t0001.3 Claude
,** TODO t0002 Build tool that updates this TODO list
,** TODO t0003 Find core links for jobhunt
#+end_example

** Why org TODO keywords instead of checkboxes

Standard org-mode workflow uses =TODO= / =DONE= keywords on headings,
not checkbox lists.  This gives us:

- =C-c C-t= to toggle TODO/DONE
- =S-<right>= / =S-<left>= to cycle TODO state
- Agenda integration via =org-agenda=
- =org-refile=, =org-archive=, tags, priorities, deadlines
- Folding and visibility cycling on each task

Checkboxes (=[ ]=) are org's lightweight mechanism for sub-step
checklists within a heading's body, not for top-level task tracking.
Using TODO keywords keeps the file idiomatic.

** Task ID format

- Top-level tasks: =t0001=, =t0002=, ... =t9999=
- Subtasks: =t0001.1=, =t0001.2=, etc.
- Deeper nesting: =t0001.1.1= (use sparingly)
- IDs are assigned once and never reused, even if a task is deleted
- IDs appear as the first token after the TODO keyword in the heading
  (after an optional priority cookie)

** Other org-mode features to use freely

These are standard org and don't require special support in =status.py=:

- Priorities: =** TODO [#A] t0005 Urgent thing=
- Tags: =** TODO t0006 Research FooCorp :research:=
- Deadlines: =DEADLINE: <2026-04-15 Wed>= on the line after the heading
- Properties drawers (e.g. =:COMPANY:=, =:URL:=) for structured metadata
- Body text, links, and sub-checklists beneath any heading

* status.py design

** Architecture

The code should maintain three layers (per Codex recommendation):

1. *Parser*: =parse_org(text) -> list[TodoItem]= -- reads org text,
   tracks source line numbers for each task
2. *Query/mutate*: filter, search, and modify the in-memory model
3. *Writer*: minimal text patching back to disk (change only matched
   heading lines, preserve everything else)

The parser should be tolerant of headings without IDs (show them
as-is) and should handle priorities, tags, and metadata lines without
breaking title extraction.

/2026-08-21:/ all three layers exist, split across two packages.  The parser is
=orglib.syntax=, reached as =orglib.parse(text).tasks()=; query and mutate are
=ortasklib.core= and =ortasklib.tasks=; the writer is still line patching plus
atomic replace.  Layer 1 answering with source spans rather than only values --
=orglib.parse(text).directories(project)= returns the span it read -- is what
lets layer 3 rewrite one section of a shared file without touching the rest.

** Heading regex

#+begin_example
^\*+\s+(?P<state>TODO|DONE)\s+(?:\[#(?P<priority>[A-C])\]\s+)?(?P<id>t\d{4}(?:\.\d+)*)\s+(?P<text>.*?)(?:\s+:(?P<tags>[\w:]+):)?\s*$
#+end_example

This captures heading level, state, optional priority, task ID,
title text, and optional tags.

/2026-08-21:/ the shape is unchanged; two alternations grew.  =MOOT= joined the
terminal states (=SUPERSEDED= is kept as a compatibility alias), and week IDs
joined the ID pattern.  The live version is =orglib.syntax.HEADING_RE=:

#+begin_example
^(?P<stars>\*+)\s+(?P<state>TODO|DONE|MOOT|SUPERSEDED)\s+(?:\[#(?P<priority>[A-C])\]\s+)?(?P<id>t(?:\d{4}|w(?:\d{2}|\d{4})[Ww]\d{2})(?:\.\d+)*)\s+(?P<text>.*?)(?:\s+:(?P<tags>[\w:]+):)?\s*$
#+end_example

** Subcommands

Use =argparse= with subparsers.  Implementation order:

/2026-08-21:/ what shipped is =add=, =apply=, =archive=, =done=, =help=,
=list=, =open=, =repair=, and =show=, registered and documented
alphabetically rather than by phase.  =context= was never built -- an LLM reads
=list= and =show= directly.  =next= and =rename= were never needed, =sync=
became =repair=, and =todo= became =open=.  =apply= and =archive= are the two
verbs this document did not foresee.  See =docs/ortask.md=.

*** Phase 1: read-only

| Subcommand  | Purpose                                     |
|-------------+---------------------------------------------|
| =context=   | Compact summary for LLM prompt injection     |
| =list=      | Print tasks (default if no subcommand given) |
| =show ID=   | Show detail for a single task (incl. body)   |

=list= flags:
- =--items N= to cap output
- =--state todo|done|all=
- =--root-only= to show only top-level tasks
- =--format plain|json|org=

JSON output makes the tool immediately useful for LLMs and scripts.

*** Phase 2: targeted editing

| Subcommand  | Purpose                           |
|-------------+-----------------------------------|
| =add=       | Append a new task (auto-assign ID)|
| =done ID=   | Mark a task DONE by ID            |

=add= supports =--parent ID= for subtasks.

*** Phase 3: richer updates

| Subcommand   | Purpose                               |
|--------------+---------------------------------------|
| =next=       | Print the next available task ID      |
| =rename ID=  | Change a task's title                 |
| =sync=       | Verify IDs, check for duplicates      |
| =todo ID=    | Reopen a completed task               |

** ID allocation

When =add= creates a new task:
1. Scan existing IDs to find the maximum top-level number
2. Assign max + 1 (zero-padded to 4 digits)
3. For subtasks, accept a parent ID and append the next sub-number

** File modification safety

The default org file should follow the shared discovery convention in
=docs/format.md=: =--file= first, then =ORTASK_FILE=, then an upward search for
=tasks.org=, =task.org=, exactly one =*.task.org=, and compatibility names. Ambiguous
matches should stop with a clear error rather than silently choosing
alphabetically.

When =ortask.py= edits the org file (per Codex recommendation):

- Prefer the task subtree under =* Tasks= when present
- Change only the matched heading line (for =done=, =todo=, =rename=)
- Append new headings in one place (for =add=)
- Preserve blank lines, body text, properties, and non-task headings
- Write to a temporary file then atomically rename (per Gemini)

** What ortask.py should NOT do

- Replace Emacs for editing.  Bulk reorganization, refiling, and
  archiving should be done in Emacs.
- Manage non-task content in the task file.
- Reformat the whole file on any edit.

/2026-08-21:/ a fourth entry belongs on that list now that there are two
commands: =ortask.py= owns Org task content and =projmgr.py= owns the registry.
=projmgr.py= writes =ortask.ini=, the registry symlinks, its =--out= stack file,
and the registry index =projects.org=; it does not edit a project's tasks.  The
index is registry data that happens to be written in Org, which is why it is on
the =projmgr.py= side of that line.

* Testing

/2026-08-21:/ =tests/test_ortask_suite.py= is that file, 180 tests, and it is
the refactor gate: run it before and after any change.  Coverage grew past this
list to XDG-isolated registry behavior, PTY coverage of the bounded inline
session, and a subprocess test that imports =orglib= with =ortasklib= blocked,
so the dependency cannot quietly reverse.  See =docs/testing.md=.

Add a pytest test file covering (per Codex recommendation):

- TODO/DONE heading parsing with and without priorities/tags
- =--items= limits and =--state= filtering
- ID allocation (next available ID)
- Marking a task done without changing unrelated lines
- Round-trip: parse then patch, verify unchanged lines are identical

* Future considerations

- Custom TODO keyword sequences (=TODO= -> =WAITING= -> =DONE=):
  defer until needed
- =CANCELLED= keyword or archive file: defer until the task list grows
- Dependency tracking via =:DEPENDS:= property (per Gemini)
- Multi-file scanning across =orgs/= and =roles/= for a global agenda
- Property-aware queries (=:COMPANY:=, =:URL:=)

/2026-08-21:/ two of these resolved, in a form worth recording.  "=CANCELLED=
keyword or archive file" became both: =MOOT= for a task that stopped mattering,
and =ort archive= for moving finished ones out.  "Multi-file scanning" became
=projmgr.py=, and the shape of the answer matters -- a registry of explicitly
registered projects rather than a glob over directories, so nothing is scanned
that the user did not name.  The other three are still open and still deferred.

Declaring the keyword set in-file with =#+TODO:= is the one addition this list
should have had: without it, =MOOT= is not a keyword to Emacs or to any other
Org parser, just a heading whose text begins with "MOOT" (=t0023=).
